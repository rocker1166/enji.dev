Analytics tools tell a merchant what is broken. They don't fix it. DynoWeb closes that gap for Shopify stores: it records how shoppers really use the store, finds where sales leak, and ships the fix as a popup, a theme change or an SEO patch the merchant can undo in one click.

I lead engineering. I wrote about 70% of the 3,000 commits, from the first Shopify app config on 13 Feb 2026 to v1.103 on 24 Oct 2026.

## Tracking, replays and heatmaps

Everything starts with a storefront script I kept under **6 KB gzipped**. It listens for clicks, rage clicks, dead clicks, error clicks, mouse shake, scroll depth, form drop-off and mobile gestures, batches them, and sends them with `sendBeacon` so nothing blocks the page. A bot guard keeps crawlers out of the numbers.

Session replays are rrweb chunks stored in Cloud Storage behind signed URLs. The player reads them straight from storage, which took a big memory load off the app server. Heatmaps went through three versions; the latest rebuilds the page DOM so the overlay lines up on any theme.

Raw events roll up daily per element, page, form and traffic source, in each shop's own timezone, so dashboards never scan raw rows. Revenue attribution first matches orders by webhook, then falls back to a weighted fingerprint (cart overlap, time, location, price, device) with hard vetoes and a 0.70 threshold.

## DynoAgent: an AI agent that can touch a live store safely

Merchants ask in plain English and DynoAgent acts: Gemini with streaming tool calls on the Vercel AI SDK, plus tool search so the model only loads the tools it needs.

The rule I built it around: **no write runs on its own**. Every write saves the store's state before it, shows an approval card, and can be reverted with one call. The same tool surface is also an **MCP server** (Streamable HTTP with OAuth 2.1 dynamic client registration), so Claude can drive DynoWeb directly.

## CRO reports and suggestions

The suggestion engine runs 17+ rule checks and 6 statistical pattern detectors (two-proportion z-tests) before it ever calls an LLM. A finding has to show up in two runs and 200+ sessions before a merchant sees it. Findings are ranked with PECTI (Proof, Ease, Cost, Time, Impact).

The CRO report is a 12-stage pipeline (KPIs, funnel, journeys, heatmap intelligence, revenue impact, false-positive filter, lift scoring, LLM narrative, schema check) that ends in a shareable page and a PDF, for about **$0.018** per report.

## Infra and cost

DynoWeb runs on GCP Cloud Run in Mumbai with Neon Postgres. I built the deploy pipeline:

- push to main builds the image, runs migrations, deploys a **canary with no traffic**, waits for ready, promotes, verifies traffic and runs a smoke test
- **auto-rollback** on any failure, plus a one-click manual rollback
- a provenance gate refuses any commit without a merged, green PR
- parity tests stop the deploy script and workflow from drifting (that drift once froze rollups silently for 5 days)

Cost work I'm proud of: I found two stale canary revisions that were **67% of the Cloud Run bill** while serving no traffic, halved the warm capacity, shrank the image registry from **127 GiB to 35 GB**, and caught a Gemini cache spike (48× normal) the day after it started.

## What I learned

The gap between analytics and action is the product. Every tool can draw a heatmap; the hard part is turning it into a safe, reversible change on a store that is making money right now. Most of my time goes into making that path trustworthy: approval before writes, undo for everything, and numbers that only show up when they're real.
